# V0.45.2 Provider 请求稳定性验证

## 目标

V0.45.2 不直接假设“连续请求一定会降低成功率”，而是先验证这个规律是否存在。

用户观察到：

- 连续跑几个任务时，更容易出现服务器端直接断开、不返回结果、502 或 timeout。
- 点击取消后，有时最后隔出来的一次反而更容易成功。

本版重点是判断这个现象是否稳定成立，再决定是否需要加入强制节流、冷却或错峰策略。

## 验证方式

为了尽量排除真实数据和前端操作干扰，验证使用临时数据库、临时配置和独立输出目录。

验证分三组：

### 1. 软件路径：连续请求 vs 间隔请求

通过软件后端 `/api/generate` 路径提交文生图。

- 连续组：5 次连续提交，不主动等待。
- 间隔组：5 次提交，每次间隔 60 秒。
- 为了观察原始请求表现，验证时关闭自动重试和强制冷却。

报告文件：

- `files/v0452_stability_probe_report_20260510_220834.json`
- `files/v0452_stability_probe_report_20260510_220834.md`

结果：

- 连续组：4 / 5 成功。
- 间隔组：5 / 5 成功。
- 连续组失败 1 次，错误为服务端 `500 stream error / INTERNAL_ERROR`。

### 2. 直接脚本路径：连续请求 vs 间隔请求

直接运行 `files/openai_text_to_image.py`，绕过软件 `/api/generate`。

- 连续组：5 次连续执行。
- 间隔组：5 次执行，每次间隔 60 秒。

报告文件：

- `files/v0452_script_probe_report_20260510_221755.json`
- `files/v0452_script_probe_report_20260510_221755.md`

结果：

- 脚本连续组：5 / 5 成功。
- 脚本间隔组：5 / 5 成功。

### 3. 软件路径连续复测

再次通过 `/api/generate` 连续提交 5 次。

报告文件：

- `files/v0452_burst_recheck_report_20260510_222717.json`
- `files/v0452_burst_recheck_report_20260510_222717.md`

结果：

- 软件连续复测：5 / 5 成功。

## 判断

当前样本不支持“连续请求稳定显著降低成功率”这个结论。

更准确的判断是：

- 确实观察到过一次连续请求中的服务端 stream/internal error。
- 但脚本连续组和软件连续复测都没有复现失败。
- 因此这次失败更像 AIAPIS / 上游服务短时间随机波动，不能证明连续请求本身就是稳定根因。

## 本版决定

不采用强制 Provider 节流或固定 60 秒冷却。

原因：

- 证据不足。
- 强制冷却会明显拖慢用户连续生成。
- 如果规律不稳定存在，强制冷却可能只是降低效率，并不能稳定提高成功率。

继续保留 V0.45.1 已验证有效的稳定性修复：

- 同 Provider 请求串行，避免真正并发打同一个 Provider。
- 可重试错误有限重试，避免无限循环。
- 每次失败重试写入历史记录。
- 取消后不再进入下一轮重试。
- 关闭网页再打开后，生成中实例仍可取消。

## 后续建议

如果后续再次出现连续失败，建议不要只凭单次现象判断。

更可靠的做法是继续积累历史记录中的失败类型：

- 502 / bad gateway
- 500 / stream internal error
- timeout
- connection reset / disconnected
- 429 / rate limit

如果未来积累到更明显的数据，例如连续请求失败率长期高于间隔请求，才适合重新加入可配置的 Provider 节流/冷却策略。

## 副作用

本版不改变生成节奏，因此不会让软件变慢。

保留的报告文件和输出图片位于 `files/` 下，作为本次验证依据，不影响软件运行。
