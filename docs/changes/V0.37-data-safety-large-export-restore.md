## 修改目标

V0.37 的目标是增强数据安全页，让大量实例、标签、节点、历史记录下的导出、备份、恢复更稳定。

本版重点：

- 数据导出改为适合大量数据的后端分批读取和任务式导出。
- 导出过程中显示进行中状态，防止重复点击。
- 新导出格式必须包含实例、输入图、输出图路径、标签、节点、历史记录、Provider 参数快照。
- 备份和恢复显示更明确的校验信息，例如实例数量、标签数量、节点数量、历史记录数量。
- 恢复前必须自动备份当前数据库。
- 恢复不能删除电脑上的图片文件。
- 恢复时对不存在的节点、实例、标签引用给出明确处理规则。
- 缩略图缓存不作为核心数据恢复，恢复后按需重新生成。
- 保存区缩略图视图状态不作为核心数据导出，但 UI 状态持久化不能被改坏。
- 清理缩略图缓存功能不能被改坏。

本版不是重新设计数据安全页，不做前端大改版，不重构 Provider，不修改生图流程。

## 当前 V0.36 基线

当前 V0.36 中：

- 备份使用 zip，包含 SQLite 数据库、配置文件、metadata。
- JSON 导出使用 `build_export_payload` 一次性读取全部表数据，再一次性写入一个 JSON 文件。
- 恢复前已经会自动创建 `pre_restore` 备份。
- 恢复不会主动删除电脑上的图片文件。
- 数据安全页已经有备份、导出、恢复、缩略图缓存清理按钮。
- 数据安全页已经用 `state.dataSafety.exporting` 等状态防止部分重复点击。

当前主要问题：

- 大量实例时，单体 JSON 导出会把所有表一次性读入内存。
- 单体 JSON 文件很大时，写入、读取和恢复校验都容易卡顿。
- 备份和恢复列表缺少明确的数据量摘要。
- 恢复时遇到坏引用虽然已有部分容错，但规则没有在 UI 和文档里明确显示。
- 恢复前无法先预览“将恢复多少实例、标签、节点、历史记录”。

## 导出格式

### 默认导出格式

V0.37 默认导出格式改为 zip 数据包。

文件名格式：

```text
AIImageManager_export_V0.37_YYYYMMDD_HHMMSS.zip
```

如果同名文件已存在，在文件名末尾追加：

```text
_01
_02
```

### zip 内部结构

zip 包内建议结构：

```text
export_manifest.json
settings.json
tables/nodes.jsonl
tables/instances.jsonl
tables/input_images.jsonl
tables/tags.jsonl
tables/instance_tags.jsonl
tables/generation_history.jsonl
tables/app_metadata.jsonl
```

说明：

- `export_manifest.json` 保存导出元信息、schema、统计数量和校验摘要。
- `settings.json` 保存设置页和 Provider 配置。
- `tables/*.jsonl` 每行一条记录，适合分批写入和分批恢复。
- 图片文件本身不进入导出包。
- 缩略图缓存不进入导出包。

### export_manifest.json

`export_manifest.json` 至少包含：

```json
{
  "app_name": "AIImageManager",
  "app_version": "V0.37",
  "export_format": "zip-jsonl",
  "export_format_version": 1,
  "exported_at": "2026-05-08T20:00:00",
  "schema_version": 3,
  "image_files_included": false,
  "thumbnail_cache_included": false,
  "tables": {
    "nodes": {"count": 0},
    "instances": {"count": 0},
    "input_images": {"count": 0},
    "tags": {"count": 0},
    "instance_tags": {"count": 0},
    "generation_history": {"count": 0},
    "app_metadata": {"count": 0}
  },
  "summary": {
    "instance_count": 0,
    "input_image_count": 0,
    "output_image_count": 0,
    "tag_count": 0,
    "node_count": 0,
    "generation_history_count": 0,
    "provider_count": 0
  }
}
```

统计定义：

- `instance_count`：`instances` 表记录数。
- `input_image_count`：`input_images` 表记录数。
- `output_image_count`：`instances.output_image_path` 非空的记录数。
- `tag_count`：`tags` 表记录数。
- `node_count`：`nodes` 表记录数。
- `generation_history_count`：`generation_history` 表记录数。
- `provider_count`：`settings.providers` 数量。

### 旧 JSON 导出兼容

V0.37 默认不再使用单体 JSON 作为导出格式。

但是为了兼容旧版本：

- 旧的单体 JSON 恢复继续支持。
- 新的数据安全页按钮显示为 `导出数据`，不再写 `导出 JSON`。
- 后端可以保留旧 `/api/exports/json` 接口，但新按钮应调用新的任务式导出接口。
- 如果保留旧 JSON 导出入口，只能作为内部兼容或调试，不作为主要 UI 入口。

## 任务式导出

### 为什么做任务式导出

大量实例时，导出可能耗时较长。前端不能一直卡在单次请求里，也不能让用户重复点击多个导出。

V0.37 采用后端任务式导出：

- 前端点击 `导出数据`。
- 后端创建导出任务，返回 `task_id`。
- 前端轮询任务状态。
- 后端按表分批读取并写入临时 zip。
- 导出完成后把临时文件改名为正式文件。
- 前端显示完成路径和导出摘要。

### 后端接口

新增接口：

```text
POST /api/exports
GET /api/exports/tasks/<task_id>
```

`POST /api/exports` 返回：

```json
{
  "task_id": "export-xxx",
  "status": "running"
}
```

`GET /api/exports/tasks/<task_id>` 返回：

```json
{
  "task_id": "export-xxx",
  "status": "running",
  "phase": "instances",
  "message": "正在导出实例",
  "processed_rows": 1200,
  "total_rows": 5000,
  "progress": 0.24
}
```

完成后返回：

```json
{
  "task_id": "export-xxx",
  "status": "success",
  "path": "D:/.../AIImageManager_export_V0.37_20260508_200000.zip",
  "summary": {
    "instance_count": 5000,
    "input_image_count": 12000,
    "output_image_count": 4800,
    "tag_count": 240,
    "node_count": 80,
    "generation_history_count": 3000,
    "provider_count": 5
  }
}
```

失败时返回：

```json
{
  "task_id": "export-xxx",
  "status": "failed",
  "error": "导出失败：..."
}
```

### 任务状态存放

导出任务状态可以先只保存在后端进程内存中。

理由：

- 本地软件单用户使用。
- 导出任务只是运行期操作，不需要跨重启恢复。
- 导出完成后文件已经在 `export/` 目录，任务记录不需要长期保存。

要求：

- 同一时间只允许一个导出任务运行。
- 如果已有导出任务运行，再次点击返回 409 或前端直接置灰。
- 任务完成或失败后保留最近状态，方便前端展示结果。
- 服务重启后旧任务状态丢失可以接受，但已完成文件仍在 `export/` 目录。

### 分批读取规则

后端导出时不能一次性 `fetchall()` 所有表。

建议每批读取：

```text
500 或 1000 行
```

每张表按主键顺序读取：

```sql
SELECT * FROM table ORDER BY id LIMIT ? OFFSET ?
```

对于没有自增 id 的表，例如 `instance_tags`，可以按：

```sql
ORDER BY instance_id, tag_id
```

对于 `app_metadata`，可以按：

```sql
ORDER BY key
```

写入方式：

- 每条记录转成 JSON。
- 一行写一条。
- 不把整表拼成大数组。

### 临时文件规则

导出时先写临时文件：

```text
AIImageManager_export_V0.37_YYYYMMDD_HHMMSS.zip.tmp
```

导出成功后：

```text
os.replace(tmp, final)
```

导出失败时：

- 删除临时文件。
- 任务状态标记为 `failed`。
- 前端显示错误。

## 恢复增强

### 恢复类型

V0.37 支持三类恢复文件：

```text
1. V0.37 zip-jsonl 导出包
2. 旧版单体 JSON 导出文件
3. SQLite zip 备份文件
```

根据文件内容判断，不只依赖后缀：

- zip 中有 `export_manifest.json`：按 V0.37 导出包恢复。
- zip 中有 `AIImageManager.data.sqlite`：按数据库备份恢复。
- json 文件且 `app_name = AIImageManager`：按旧 JSON 导出恢复。

### 恢复前自动备份

恢复前必须自动创建 `pre_restore` 备份。

规则：

- 只要开始执行恢复写入，就必须先备份当前数据库和配置。
- 预览恢复文件时不创建备份。
- 恢复失败时，不能删除 `pre_restore` 备份。
- 恢复接口返回 `pre_restore_backup` 路径，前端显示。

### 恢复不会删除图片文件

所有恢复方式都只替换或写入数据库和配置。

明确禁止：

- 删除电脑上的原图。
- 删除电脑上的输入图。
- 删除电脑上的输出图。
- 删除缩略图缓存之外的任何图片文件。
- 复制原图到导出包。
- 从导出包还原原图到电脑。

数据库中的图片路径按导出数据恢复。

### zip-jsonl 恢复流程

V0.37 zip-jsonl 恢复流程：

1. 校验 zip 可打开。
2. 读取 `export_manifest.json`。
3. 校验 `app_name`、`export_format`、`schema_version`。
4. 校验必要文件存在。
5. 创建 `pre_restore` 备份。
6. 清空目标数据库中的核心表。
7. 按顺序分批导入：
   - `nodes`
   - `instances`
   - `input_images`
   - `tags`
   - `instance_tags`
   - `generation_history`
   - `app_metadata`
8. 保存 `settings.json` 到配置文件。
9. 重新执行 `init_db`，确保 schema 和 metadata 正常。
10. 返回恢复摘要和引用修正摘要。

### 引用处理规则

恢复时必须明确处理坏引用。

规则：

- 实例引用的节点不存在：该实例 `node_id` 置空，归到未分配节点范围。
- 输入图引用的实例不存在：跳过该输入图记录。
- 标签关联引用的实例不存在：跳过该标签关联。
- 标签关联引用的标签不存在：跳过该标签关联。
- 节点的父节点不存在：该节点提升为根节点，即 `parent_id = null`。
- 历史记录不强制依赖实例，按原数据保留。
- app metadata 中缺失或旧值不影响恢复，恢复后由 `init_db` 修正必要 metadata。

恢复结果返回：

```json
{
  "restored": true,
  "summary": {
    "instance_count": 5000,
    "input_image_count": 12000,
    "output_image_count": 4800,
    "tag_count": 240,
    "node_count": 80,
    "generation_history_count": 3000,
    "provider_count": 5
  },
  "reference_fixes": {
    "instances_node_missing_set_null": 3,
    "input_images_skipped_missing_instance": 2,
    "instance_tags_skipped_missing_instance": 1,
    "instance_tags_skipped_missing_tag": 1,
    "nodes_parent_missing_set_null": 1
  },
  "pre_restore_backup": {}
}
```

前端恢复完成后显示：

```text
恢复完成：实例 5000 · 标签 240 · 节点 80 · 历史 3000
已自动创建恢复前备份：...
修正引用：节点缺失 3，输入图跳过 2，标签关联跳过 2
```

如果没有引用修正：

```text
引用检查通过，无需修正。
```

## Provider 参数快照

V0.37 导出必须保留 Provider 相关数据。

包含两类：

1. 当前设置中的 Provider 配置。
2. 历史记录和实例生成参数中的 Provider 参数快照。

具体要求：

- `settings.json` 完整保存 `providers` 配置。
- `generation_history.params_json` 原样导出。
- `instances.generation_params_json` 原样导出。
- `instances.provider` 原样导出。
- 不重新计算旧历史记录中的 Provider 参数。
- 不因为当前设置页 Provider 已删除而修改旧历史记录。

说明：

- Provider 是用户自己写的代理商名字。
- adapter 才是 `openai / google / other`。
- 导出和恢复必须尊重 V0.26 的 Provider 能力体系，不丢失配置字段。

## 缩略图缓存

缩略图缓存不是核心数据。

V0.37 规则：

- 导出包不包含 `cache/thumbnails`。
- 备份包不包含 `cache/thumbnails`。
- 恢复不恢复缩略图缓存。
- 恢复后如果原图路径有效，缩略图会按 V0.34 逻辑重新生成。
- 清理缩略图缓存按钮保持原功能。

数据安全页说明文字中保留或增加：

```text
缩略图缓存不是核心数据；恢复后会按需重新生成。
```

## UI 状态与保存区缩略图视图

保存区缩略图视图状态属于 UI 状态，不是核心业务数据。

V0.37 规则：

- 导出核心数据时不需要包含 `save_view_mode`。
- 恢复核心数据时不强制改变当前 UI 状态。
- 现有 UI 状态持久化不能被改坏。
- V0.36 的保存区缩略图视图不能被改坏。
- 切换缩略图/列表、懒加载、悬停预览、大图弹窗继续保持。

## 数据安全页交互

### 导出数据

点击 `导出数据`：

1. 设置 `state.dataSafety.exporting = true`。
2. 调用 `POST /api/exports`。
3. 保存 `task_id`。
4. 每 500ms 或 1000ms 轮询任务状态。
5. 显示进度文字。
6. 成功后显示路径和摘要。
7. 失败后显示错误。
8. 完成或失败后停止轮询。

如果用户切换页面：

- 导出任务可以继续运行。
- 回到数据安全页时可以继续显示当前任务状态。
- 如果实现复杂，V0.37 可以只在当前页面显示轮询，任务完成后文件仍然存在。

### 选择恢复文件

选择恢复文件后：

1. 保存路径到 `selectedBackupPath`。
2. 调用 `POST /api/restore/preview`。
3. 显示恢复摘要和警告。
4. 如果预览失败，禁用恢复按钮并显示错误。

### 恢复当前文件

点击恢复：

1. 必须已有有效预览。
2. 必须二次确认。
3. 如果有生成任务正在进行，禁止恢复。
4. 调用 `POST /api/restore`。
5. 后端先创建 `pre_restore` 备份。
6. 恢复完成后显示摘要。
7. 提醒用户刷新页面后继续使用。

## 可能副作用与处理

### 导出格式变化

影响：

- 默认导出文件从 `.json` 改成 `.zip`。

处理：

- 按钮改为 `导出数据`，避免暗示格式一定是 JSON。
- 旧 JSON 恢复继续支持。
- 文案说明“新导出为数据包，不包含图片文件”。

### 导出任务状态只保存在内存

影响：

- 如果导出过程中关闭软件，任务状态会丢失。

处理：

- 这是本机单用户软件，可以接受。
- 临时文件失败时下次清理。
- 已完成导出文件不依赖任务状态。

### 分批导出实现更复杂

影响：

- 后端代码比单体 JSON 导出多。

处理：

- 逻辑集中在 `backend/backup.py` 和 `backend/api.py`。
- 不改数据库 schema。
- 加测试覆盖大量数据分批导出。

### 恢复时坏引用被修正或跳过

影响：

- 恢复后的数据可能和坏导出文件不是逐字完全一致。

处理：

- 明确规则。
- 返回修正统计。
- UI 显示修正摘要。
- 不因为少量坏引用导致全部恢复失败。

### 备份 metadata 增加字段

影响：

- 旧备份没有新字段。

处理：

- 读取旧备份时兼容缺失字段。
- 旧备份显示 `摘要不可用`。

### 大量数据导出时仍可能较慢

影响：

- 即使分批，几万条记录仍然需要时间。

处理：

- 显示进度。
- 防重复点击。
- 后端使用临时文件，失败不污染正式导出。
