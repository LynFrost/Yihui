## 修改目标

V0.38 的目标是新增独立的 `标签管理` 页面，方便在大量正在使用的 TAG 下统一整理 TAG 名称和 TAG 归并关系。

本版重点：

- 新增独立 `标签管理` 页面。
- 页面只管理正在使用的真实 TAG。
- 显示每个正在使用的 TAG 对应的实例数量。
- 支持搜索 TAG。
- 支持重命名 TAG。
- 支持合并 TAG。
- 标签管理操作只影响软件数据库，不影响电脑上的图片文件。
- 标签管理操作后，保存区实例 TAG、批量 TAG、标签筛选下拉要同步更新。
- 标签统计排除虚拟筛选项 `无` 和内部值 `__untagged__`。
- 标签管理兼容节点筛选，但 TAG 本身仍然是全局 TAG。
- 标签管理兼容普通列表模式和缩略图模式。

本版不做：

- 不管理未使用 TAG。
- 不显示未使用 TAG。
- 不提供删除未使用 TAG 功能。
- 不在标签管理页新建 TAG。
- 不做批量修改 Provider。
- 不重构 Provider 能力体系。
- 不改变保存区普通列表和缩略图视图的主要 UI。

## 讨论结论

本版采用独立页面方案。

原因：

- 生图管理页已经承担操作区、保存区、筛选、节点、批量操作、缩略图视图等功能，再把 TAG 管理放进去会继续挤占空间。
- 标签管理是低频整理功能，独立页面更清楚，也不会干扰保存区日常浏览。
- 独立页面可以在不改变保存区布局的情况下放下搜索、统计、重命名、合并等操作。

TAG 范围收口为：

- 只展示 `正在使用的 TAG`，也就是至少绑定了一个实例的真实 TAG。
- 不展示数据库里可能遗留的未使用 TAG。
- 不提供“新建 TAG”，因为 TAG 必须通过操作区、保存区实例或批量添加绑定到实例后才算投入使用。
- 不提供“删除未使用 TAG”，因为本版不管理未使用 TAG。

## 标签管理页布局

标签管理页顶部一行显示：

```text
标签管理    搜索 TAG    刷新    状态
```

页面主体显示 TAG 列表。

每个 TAG 项显示：

```text
TAG 名称    实例数量    重命名    合并
```

说明：

- `实例数量` 是当前数据库中绑定该 TAG 的实例数量。
- TAG 名称过长时可以截断显示，但必须通过 `title` 或悬停浮层看到完整名称。
- 搜索只按 TAG 名称搜索，不按实例内容搜索。
- 搜索为空时显示全部正在使用的 TAG。
- 搜索结果为空时显示空状态文字，不创建 TAG。

## 正在使用的 TAG 定义

正在使用的 TAG 指满足以下条件的 TAG：

- 存在于 `tags` 表。
- 至少存在一条有效 `instance_tags` 关联。
- 对应实例存在于 `instances` 表。
- TAG 名称不是空字符串。
- TAG 名称不是内部值 `__untagged__`。

虚拟筛选项 `无` 不是 TAG。

内部值 `__untagged__` 不是真实 TAG。

标签管理页、统计、重命名、合并中都不能把 `无` 或 `__untagged__` 当作真实 TAG。

## 后端接口

### 列表接口

新增：

```text
GET /api/tag-management
```

查询参数：

```text
q=搜索关键词
```

返回：

```json
{
  "items": [
    {
      "id": 1,
      "name": "portrait",
      "usage_count": 12
    }
  ],
  "total": 1
}
```

排序规则：

- `usage_count` 从高到低。
- `name` 按不区分大小写排序。

这个接口只返回正在使用的真实 TAG。

### 重命名接口

新增：

```text
PATCH /api/tag-management/<tag_id>/rename
```

请求：

```json
{
  "name": "new tag name"
}
```

规则：

- 只能重命名正在使用的真实 TAG。
- 新名称不能为空。
- 新名称不能是 `无`。
- 新名称不能是 `__untagged__`。
- 新名称不能和其他 TAG 名称重复。
- 如果用户想把两个 TAG 变成一个 TAG，应使用合并功能，不通过重命名隐式合并。
- 重命名需要在事务中完成。

返回：

```json
{
  "item": {
    "id": 1,
    "name": "new tag name",
    "usage_count": 12
  },
  "tags": ["new tag name", "another used tag"]
}
```

其中 `tags` 返回操作后的全部正在使用 TAG 名称列表，用于刷新前端 TAG 选项。

### 合并接口

新增：

```text
POST /api/tag-management/merge
```

请求：

```json
{
  "source_tag_ids": [1, 2],
  "target_tag_id": 3
}
```

规则：

- source 和 target 都必须是正在使用的真实 TAG。
- target 不能包含在 source 中。
- source 至少选择一个。
- source 合并到 target 后，source 原来关联的实例都改为关联 target。
- 如果某个实例原本已经有关联 target，不重复插入。
- 合并后 source TAG 不再被任何实例使用时，可以从 `tags` 表删除。
- 合并操作必须二次确认。
- 合并必须在事务中完成。
- 合并失败时不能出现一部分 TAG 已移动、一部分 TAG 未移动的半完成状态。

合并后返回：

```json
{
  "target": {
    "id": 3,
    "name": "target tag",
    "usage_count": 20
  },
  "removed_source_ids": [1, 2],
  "tags": ["target tag", "another used tag"]
}
```

其中 `tags` 返回操作后的全部正在使用 TAG 名称列表，用于刷新前端 TAG 选项。

## 前端状态同步规则

标签管理页执行重命名或合并后，必须同步更新：

- `state.tagOptions`
- 保存区实例上显示的 TAG
- 保存区标签筛选下拉
- 操作区添加 TAG 下拉
- 保存区实例添加 TAG 下拉
- 批量添加 TAG / 删除 TAG 的选项
- 缩略图视图下的筛选结果

同步后需要重新加载保存区当前数据。

如果当前保存区正在筛选 TAG：

- 重命名 TAG：当前筛选条件中如果包含旧 TAG 名称，自动替换为新 TAG 名称。
- 合并 TAG：当前筛选条件中如果包含 source TAG，自动替换为 target TAG。
- 如果多个 source TAG 都被当前筛选选中，替换后只保留一个 target TAG。
- 如果当前筛选条件包含 `__untagged__`，不受重命名和合并影响。
- 筛选条件变化后写入 UI 状态持久化。

标签管理操作后：

- 清空保存区当前页批量选择。
- 保留当前节点筛选。
- 保留搜索、来源筛选、方式筛选、排序、每页数量。
- 使用现有避免空白页逻辑，不能出现空白页。

## 节点兼容规则

TAG 是全局数据，不属于某一个节点。

标签管理页显示的 `实例数量` 是全局数量，不随当前节点筛选变化。

原因：

- 同一个 TAG 可以出现在多个节点下。
- 标签管理页的目标是整理全局 TAG，而不是只整理某个节点局部 TAG。
- 节点筛选仍然在生图管理页生效，不改变 TAG 本身的全局属性。

如果用户在某个节点下切到标签管理页：

- 标签管理页仍显示全局正在使用 TAG。
- 返回生图管理页后，原节点筛选保持不变。

## 普通列表和缩略图视图兼容

标签管理操作不直接改变保存区视图模式。

在普通列表模式下：

- TAG 重命名或合并后，实例卡片上的 TAG 文案应立即更新。
- 标签筛选下拉应立即更新。

在缩略图视图下：

- 缩略图布局不显示完整 TAG 信息，但筛选下拉和筛选结果必须更新。
- 当前缩略图视图状态保持不变。
- 悬停预览、点击查看大图、缩略图缓存不能被改坏。

## 确认与错误提示

重命名：

- 用户点击 `重命名` 后弹出输入框。
- 回车确认，ESC 取消。
- 新名称为空、重复、非法时，显示错误并不提交。

合并：

- 用户点击 `合并` 后弹出合并对话框。
- 选择一个或多个 source TAG。
- 选择一个 target TAG。
- 点击确认前必须二次确认。
- 二次确认文案必须说明：合并只修改数据库 TAG 关联，不删除电脑上的图片文件。

推荐确认文案：

```text
确定将选中的 TAG 合并到「目标 TAG」吗？此操作只修改软件数据库中的 TAG 关联，不会删除电脑上的图片文件。
```

失败提示：

- 后端返回错误时，在标签管理页顶部显示错误。
- 不刷新掉用户当前输入内容，方便修改后重试。
- 合并失败不能让前端误以为成功。

## 副作用与风险

本版可能带来的影响：

- 重命名 TAG 会立即改变保存区实例显示、筛选下拉、批量 TAG 选项，这是预期行为。
- 合并 TAG 会让 source TAG 从正在使用 TAG 列表中消失，这是预期行为。
- 如果当前保存区正在用 source TAG 筛选，合并后筛选条件会被替换为 target TAG，当前可见结果可能变化。
- 如果当前筛选条件中同时包含多个 source TAG，合并后会折叠成一个 target TAG。
- 标签管理页显示的是全局 TAG 数量，不随当前节点变化，避免用户误以为 TAG 属于某个节点。
- 合并操作涉及 `instance_tags` 批量更新，必须使用事务，否则中途失败会导致 TAG 关联不一致。
- 重命名不能隐式合并到已有 TAG，否则用户可能在无确认的情况下把两个 TAG 混到一起。
- 标签管理页不管理未使用 TAG，所以数据库中历史遗留的未使用 TAG 可能继续存在；它们不会显示在本页，也不会影响保存区使用。

必须避免：

- 不能把虚拟 `无` 写入 `tags` 表。
- 不能把内部值 `__untagged__` 当作真实 TAG。
- 不能删除电脑上的图片文件。
- 不能破坏 V0.37 的备份、导出、恢复。
- 不能破坏缩略图缓存、缩略图视图、节点管理、批量管理、Provider 能力体系。
